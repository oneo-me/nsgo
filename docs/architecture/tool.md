# The nsgo tool

`cmd/nsgo` builds, runs, tests and packages apps from their `nsgo.yaml`, shelling out to `go` and, for Apple targets, Xcode's tools. It follows NSH's `nsh-cli` (`nsh/docs/dev/tooling.md` and `embedding.md`). Read this before changing `cmd/nsgo`.

## Output

Every command prints one line per step and the details only when a step fails, as NSH's CLI does (`nsh/crates/nsh-cli/src/ui.rs`, `nsh/docs/dev/tooling.md` "Output"): `✓` a step that finished, `→` where to find something, `•` what a device or server did, `warn` and `error` for problems. The tool's lines are indented two spaces, so the app's own lines stand apart. On a terminal a step that takes a while shows a spinner in its line with what it does at the moment (`stage`: compiling TSX, compiling Go, signing…), and colors are used unless `NO_COLOR` is set; redirected, only the result lines appear. All of it is stderr.

`nsgo build` and `nsgo dev` start with the NSGo version the tool was built from, the app's name and version and the targets, then what they do. `nsgo build` times each package and measures its directory, so each target's line reads `✓ built macos_arm64 (1.4s, 23.4 MB)`, numbered as `[2/5]` in a build of several targets, which ends with their number, time and total size. Targets building at once show a spinner line each, in the targets' order, and what one says while it builds (`detailIn`, `warnIn`) waits for its `✓` line, so their lines never interleave. `nsgo dev` reports each build's time, the app's start and whether it watches for changes, which it does unless `dev.hot_reload` is false. A tool's output, Go's or Xcode's, appears indented under `error` only when it fails.

## Dev loop

`nsgo dev` (`dev.go`) starts a dev server on `-port` (8080), or the next free port, listening on every interface. Dev builds take the `nsgodev` tag, which links `nsgo`'s dev client (`dev_client.go`): it follows the server's `/_nsgo/events` and shows a failed build's output in an overlay over the running app, as it shows the app's own render failures; its Reload button posts `/_nsgo/reload`. `-fps` and `-lang` start the app with the engine's flags `--nsgo-fps` and `--nsgo-lang` (`nsgo`'s `flags.go`), which `nsgo.Run` takes out of `os.Args` before `main`: as arguments on desktops and through `simctl` or `devicectl`, as an intent's `nsgo-` extras that `NsgoActivity` turns back into arguments on Android, and in the page's query, which `nsgo.js` puts in `go.argv`, on the web. `-limits`, alone or with limits as `tsx.ParseLimits` reads them, runs a TSX app sandboxed as `tsx.View` runs a package, with every module, its bundles replacing it rather than updating it in place: `compiler.devLimits` and `compiler.devCapabilities`, `nsgo.yaml`'s capabilities as base64url JSON, are set through `-X`.

The server finds the app through `NSGO_DEV_SERVER`, which the simulator gets as `SIMCTL_CHILD_`; Android and iPhones, which pass no environment, get it with `-ldflags -X`, Android at `127.0.0.1` through `adb reverse`, removed when the run ends, an iPhone at the Mac's LAN address.

The web target is served from the same server; its page shows the overlay itself and loads each build. A run ends with the app, and without hot reload a failed first build ends it. `-release` builds as `nsgo build` does, for measuring with `-fps`. `-trace` builds with `-X nsgo.devTrace=1`: the dev client sets `engine.Trace` for every engine of the process and posts each commit to `/_nsgo/trace`, printed as `nsgo test -trace` prints a batch (`driver.WriteTrace`), labeled by its number, with the app's output. With it `driver.TraceCauses` is set, also by `nsgo test -trace` (`nsgotest`): each signal write records its callers and each computation run its kind, and a tree's commit takes them into `MountBatch.Causes`, which `driver.WriteTrace` prints above the items. A write's site is its first caller outside `core` and NSGo's internal packages, or NSGo's outermost function for writes NSGo made itself, as an animation's; writes that changed no tree count toward the next tree that commits. `-highlight` builds with `-X nsgo.devHighlight=1`: the dev client mounts `core.UpdateHighlights` over the app, which outlines the views each commit's items created, moved, restyled or filled anew, other than its own, posting them once the commit is done, so its own commits outline nothing. Dev builds' files take the `nsgodev` tag, so `nsgo check` in NSGo's repository vets the root package with it too. `-devtools` builds with `-X nsgo.devDevtools=1` and serves DevTools, plain HTML and JavaScript embedded in the tool (`devtools/`), at `/_nsgo/devtools/`. The dev client sets `devtools.Enabled` before any graph starts, as `Run` starts tracing and DevTools once (`startDevClient`) before it starts the engine, for an app's function as for a root view, so `core` records what DevTools read: the component each scope renders, the signals each owner makes and every computation with how often it ran, each with its site, the first caller outside the packages that run apps, as a whole path for the editor's link; a binding takes its component's. It registers each tree but the first one of an app that opens windows, which shows no view, in `internal/devtools`, whose `Surface` the client drives on the graph's goroutine through `Post`. The page's commands reach the app as `devtools` events on `/_nsgo/events`, and the app posts its answers and each commit, a quarter of a second's at a time, to `/_nsgo/devtools/out`, which the server passes to pages following `/_nsgo/devtools/stream`. Both take only their JSON content types, which another site's page cannot send without a preflight the server never allows, and no `Origin` but the server's own. Pick and the inspected outline draw in `UpdateHighlights`' overlay, which takes the pointer while picking and hit-tests past its own views; the recorder hears presses and edits in `Tree.Dispatch` and names views by test ID, then role and label, then text. Unset, `devtools.Enabled` costs a nil check where a signal, a computation or a component is made, a computation runs and a scope goes. With it, and under `-trace` and `nsgo test -trace`, which set it too, each commit's causes name the computations it ran by kind and site with their own time, not counting what their writes ran next, and the app's time before it and its layout's. `driver.Apply` times each batch on the platform's main thread for `driver.Applied`, which the client joins to its commit; every backend applies through it but Android's, whose Java runtime applies batches. A write's site is read as the write is made, and one in tsx's Go asks `devtools.ScriptSite`, which tsx sets for the JS its runtimes run now, mapped by goja or the page through the bundles' source maps, so a TSX app's sites are its TSX lines, relative to the app, which the page joins to the directory `/_nsgo/devtools/project` names. Recorded scrolls are kept per scroll view and become one `ScrollTo` once the user does something else, the view rests or recording ends. A phone is told the address the machine sends from first (`outboundIP`), as virtual networks' interfaces may come before the Wi-Fi's. The web page's Go finds the server at the page's origin and leaves build failures to the page. `-device` picks a simulator by name or UDID, booting it, or an adb serial or an emulator's AVD name.

## TSX apps

The tool finds a package's TSX entries in its `compiler.App(src, "App.tsx")` calls (`bundle.go`), compiles each with `tsx/bundler` from the app's directory and adds the bundles to the package with a file calling `compiler.Bundled`, through `go -overlay`, built with the `nsgo_bundled` tag, which leaves the compiler out. The overlay names the package's directory as `$PWD` spells it and by its real path, since `go` names the files by either. `nsgo dev` compiles hot bundles ([TSX](tsx.md#developing)) and watches the files they compile from apart from the Go ones: a change of them alone compiles the TSX again and sends `bundle <entry>` over `/_nsgo/events`, which `/_nsgo/bundle?entry=` serves, with no Go build; a failed compile shows as a failed build does.

A web release's bundles are split ([TSX](tsx.md#split-bundles)): `buildWeb` writes each chunk as `chunks/<module>.<10 hex>.js` before the Go build, and the file the overlay adds gives `compiler.BundledChunks` their URLs.

## New apps

`nsgo init` (`init.go`) writes an app of `-template` `go` (the default), `tsx` or `mixed`, NSH's `ts` and `mixed` templates: `nsgo.yaml` and tests each, and for TSX a main package embedding the sources, `App.tsx`, `app.test.tsx`, `tsconfig.json` and `.gitignore`; `mixed`'s `App.tsx` imports a Go component, function and class `native.go` registers under `<slug>/native`. It refuses a directory holding any of its files. `TestInitTemplates` writes each and runs its tests against the checkout.

## Catalogs

`i18n.go`, `i18n_message.go`, `i18n_gen.go` and `i18n_build.go` check packages' catalogs and write their Go code ([languages](languages.md#the-tool)): `dev`, `build` and `test` before they compile, `check` without writing, and `nsgo i18n` for one directory. `dev` watches the YAML files of the directories it watches, and the app's catalogs before it imports them.

## Modules

The first step of `dev`, each rebuild's included, and of `build`, `check` and `test` lists the app's packages and their dependencies (`appPackages` in `i18n_build.go`). When go list says the module's `go.mod` or `go.sum` lacks what one of them comes from, as after pasting an app that imports `ui` into a module made with `go get github.com/nsgo-dev/nsgo`, the tool runs `go mod tidy` and lists them again, so the build after it finds them. It then requires `tsx` at the NSGo version the app requires, since the types `check` and `dev` write import it through an overlay `go mod tidy` cannot see; writing them after a tidy the user ran does the same.

## Checking

`nsgo check` (`check.go`) checks the catalogs, runs `go vet ./...` and, for an app with a `tsconfig.json`, as only a TSX app has, writes the declarations of the modules its TSX imports to `.nsgo/types`, with `.nsgo/tsconfig.json`, and runs TypeScript 7's checker (`tsgo`, a pinned version of `github.com/microsoft/typescript-go` that `go run` builds and caches) on the app's `tsconfig.json`, which extends it. A directory without `nsgo.yaml`, such as the repository's root, is checked as a tree of packages: catalogs and `go vet` alone. `-target` vets again for each target named, in the environment its build sets (`GOOS`, `GOARCH`, cgo with Xcode's clang for iOS), so code behind another platform's build tags is checked from a Mac too. The declarations come from the app's own program: the tool builds its main package with a file, added through the overlay, whose `init` runs after the package's others, so after every `tsx.Register`, writes them and exits before `main`. It checks with `go list` that the file is in the package before it builds, so the app itself never runs. A directory with `nsgo.yaml` but no Go, such as the TSX app a package holds, has nothing to vet, and its declarations are those of every module NSGo gives, from a main package the tool writes in `.nsgo/typesmain` importing them all, since the host decides which its packages may import. `nsgo dev` writes them too, for editors, after each Go build of an app with a `tsconfig.json` once the app has started; a failure only warns.

## Doctor

`nsgo doctor` (`doctor.go`) looks at the machine, starting nothing, and lists the tools it found, then each target with whether it builds and runs there: `✓`, `✗` with what to install or connect, or `–` for what no tool could change, such as another system's apps or Apple's on a Mac-less machine. It reuses the lookups the commands make, `findAdb`, `findNDK`, `findBrowser`, `simulators`, `iosDevices` and `canOpenMiniProgram`, so it and they agree, and reads Linux's libraries from the library directories, as the backend's `dlopen` would find them, with GTK's version from its file's name. It fails only when Go is missing or older than go.mod's.

## Tests

`nsgo test` (`test.go`) runs `go test -json` and prints a line per test, with a test running the package's `*.test.tsx` files (`tsxtest.Run`) added through the overlay when it has any, a failure's output under it (a subtest's under its own line), a tally, and with `-junit` a JUnit report, a suite per package. Given a TSX entry rather than a directory, it runs `TestSteps` instead, which opens the entry on the network, lets it run 1.2 s and takes the steps standard input holds, none from a terminal (`tsxtest.RunSteps`, NSH's `nsh test <entry>`). A directory without `nsgo.yaml` runs every package under it, and one ending in `/...` names its tree, so the tool alone tests libraries and this repository; the TSX tests it adds skip `testdata` and directories holding an `nsgo.yaml` or `go.mod` of their own. `-bench` passes `-bench` and, unless `-run` is given, `-run '^$'`; `go test -json` ends benchmarks with no event, so each result line it prints counts as a passed test. `-run` filters; `-trace` sets `NSGO_TEST_TRACE`, under which `nsgotest` prints each batch under its step with its items and the commit's time.

`-target` runs the tests on a platform, a process per test ([testing](testing.md#on-a-platform)), the TSX ones among them; a package whose tests link no platform, as a library's, runs headless in the target's runtime, so `tsx`'s run on the page's engine with `-target web`: the test binary carries the app's TSX, data and assets, since it runs where its sources are not, and starts the app from the bundles compiled ahead, as packages do. `-fps` has the test hosts of macOS, Windows, Linux and the iOS simulator log their performance monitor's readings each second, and those of the web and Android the engine's alone, with no frames, which the tool prints as they come (`NSGO_TEST_FPS`, `testhost.Options.FPS`), as it prints a test's marks of what they measure (`nsgotest`'s `Mark`, logged as `nsgo: perf mark`) with or without it. `-env KEY=VALUE` adds to the tests' environment on every target, the only variables a phone's tests see. macOS, Windows and Linux on this machine, the web in a headless Chrome, Chromium or Edge it finds (or `NSGO_BROWSER`) over the DevTools protocol (`cdp.go`, on `x/net/websocket`), the iOS, tvOS and watchOS simulators through `simctl launch` (a watch's test host enters touches where the SwiftUI host's do, at Go's hit testing, and scrolls a scroll view as `ScrollTo` does, since watchOS posts no touches for an app), and Android through `am start` with the test in an intent extra and its output read back from the device's log.

## Packages

`nsgo build` strips symbols, paths and VCS stamps (`nsgo dev` keeps symbols unless `-release`) and writes a directory per target under `build.output`, building `build.jobs` targets at once (`-jobs`; half the CPUs by default, as each `go build` uses them all). Each builds from a copy of the project, which holds what one target's build sets, and the caches they share are written whole by content or under a lock, as the Android debug key is; the first target to fail stops the others and leaves no directory. Every build of an app, its tests' on a target too, takes `GOEXPERIMENT=nojsonv2`, encoding/json's first implementation, about 1 MB smaller on the web, 450 KB on Android and 100 to 450 KB on desktops, unless its packages or dependencies import `encoding/json/v2` or `jsontext`, or `GOEXPERIMENT` names the experiment (`smallJSON` in `build.go`):

- macOS: `<name>.app`, signed with `sign.identity`, else ad hoc. iOS and tvOS: `<name>.app` and `<name>.ipa`, signed with `sign.profile`, else unsigned; tvOS's are iOS's (`appleOS` in `ios.go`) with its SDK, `GOOS=ios` still, its device family and an icon the Apple TV layers. watchOS: `<name>.app` alone, the Go executable built with the `nsgowatch` tag and the SwiftUI host (`watch/Host.swift`, `watchos.go`) compiled by swiftc into an object its external linker takes, ad hoc signed for the simulator and unsigned for devices; a watch-only app, arm64 alone, so watchOS 26 on Series 9, Ultra 2 and later. Android: `<name>.apk`, signed with `sign.keystore`, else the project's debug key.
- Windows and Linux: the executable with the resources beside it.
- With `-embed`, for apps of their own to embed ([embedding](embedding.md)): iOS's `<module>.xcframework` (of dynamic frameworks with `-dynamic`) with `<name>Resources`, Android's `<name>.aar`, and no package for other targets.
- Web: `index.html`, `manifest.webmanifest`, `nsgo.json`, which names the rest for the loader, and every other file named by its content (`app.<10 hex>.wasm`, `nsgo.<10 hex>.js`, `page.<10 hex>.css`, `mount.<10 hex>.js`, `web.host`'s module as `host.<10 hex>.js`, a TSX app's bundle and chunks, the scripts its realm runs as `nsgo-runtime.<10 hex>.js` and each resource), so hosts cache them for good. The page runs the app with the loader, from files of its own and none inline, so a Content-Security-Policy needs no `'unsafe-eval'` ([embedding](embedding.md#on-the-web)).
- Mini programs (`miniprogram_wechat`, `_qq`, `_alipay`, `_douyin`): a project for the platform's developer tool, its runtime from `miniprogram/common` and the platform's render layer, and the module brotli compressed in the subpackage `nsgo-app`, with `miniprogram.appid`'s entry for the platform (else the AppID the tool wrote, else WeChat's tourist one) and `miniprogram.custom_navigation`. It is built stripped, without the dev client, and left out of `all`, which says so, while `miniprogram` names the four; past 2 MB it is built again without inlining, then refused ([mini programs](miniprogram.md#the-package)). `-run` and `nsgo dev` open WeChat's with DevTools' command line, whose service port must be on, and the others with their apps on macOS; the tools compile each dev build again.

`resources/` ships at each package's resource root: beside the executable on Windows and Linux, beside the page on the web, in the bundle's `Contents/Resources` on macOS, at the bundle's root on iOS and in the APK's assets on Android, which with iOS leave out the paths `mobile.exclude_resources` lists. `imageload.ResourceRoot`, the web backend and Android's APK reader resolve `asset:` and font paths against it. App icons are drawn in Go; an Apple TV's is `icon.tvos`, Xcode's brand assets collection or a wide image, else the PNG over its own edges' color, as a two-layer image stack with top shelf images, since `actool` compiles no `.icon` for tvOS; an Apple Watch's is `icon.watchos`, its own `.icon` or square image, else `icon.apple`, which actool draws in circles; `actool` compiles Apple's `.icon` files, its output kept in the user cache by its version and the icon's content, and a Windows icon links from a `.syso` in the app's package directory, the only place Go links one from.

Native libraries come with the packages that hold them (`natives.go`): when the app's build links `base/terminal`'s library package, as `go list -deps` tells, libghostty-vt goes into a macOS app's `Contents/Frameworks` and an iOS app's `Frameworks/GhosttyVT.framework`, signed before the app so its signature seals them: ad hoc for macOS and the simulator, with the store's identity, or in Xcode's signing script for a device. `-embed` frameworks, Android and tvOS packages carry none yet ([roadmap](../roadmap.md#terminal)).

`build_number` sets `CFBundleVersion` and `versionCode`, else they follow `version`. `android.permissions` adds `uses-permission`s to the APK's manifest beyond the runtime's, a name without a dot under `android.permission.`; `-embed` libraries leave them to the host's manifest. `apple.info` adds string entries to the Info.plist of macOS and iOS packages, such as the `NSMicrophoneUsageDescription` recording needs. `file_types` registers the documents a macOS app opens (`filetypes.go`): `CFBundleDocumentTypes`, with the type exported as the app's own when its ID is under the app's and imported otherwise, so an app opening another's format ranks as an alternative rather than claiming it; other packages leave them out ([roadmap](../roadmap.md#application-and-windows)). `windows.command_line` adds a console-subsystem `<name>.com` beside the GUI `<name>.exe` (`windows_command.go`), forwarding arguments, standard streams and the exit code to it, so command lookup can run the app without changing its Explorer and Start menu behavior; the console's Ctrl+C and close reach the companion alone, which ends the app, as does the job it puts the app in when the companion is killed. `appearance` starts the app light or dark through `-X`, and sets `UIUserInterfaceStyle`, macOS's Aqua appearance, Android's activity theme and the page's `color-scheme`. `-run` starts the package of the first target this machine runs: the app, the iPhone's or Apple TV's, the simulator's, the Android device's, or the site served with a CDN's cache headers. `-device` picks the device as `nsgo dev`'s does; Xcode signs the iPhone's package again for `-team`, as in the dev loop, since devices install only development builds.

### Installers

Unless `build.installers` is false, `installer.go`, `dmg.go`, `nsis.go`, `linuxpkg.go` and `appimage.go` add what users install the desktop packages from, named `<slug>-<version>-<system>-<arch>` (`releaseName`) by the app's slug (`packageSlug`: its name in lowercase ASCII words, else its ID's last part), so a release page tells its files apart by system; MyGo's CLI makes them so (`mygo/cmd/mygo`) without the system's name. The Linux packages take it too, since dpkg and pacman read the name and version from inside. `release.go` moves each into `build.output`'s `releases` directory with a `<file>.sha256`. That directory holds everything to hand out, the one place to look: the installers, IPAs and APKs copied from their packages, the site zipped as `<slug>-<version>-web.zip` and the mini programs' projects in `miniprogram/<platform>/`, but no simulator's or watchOS's bundle. Machines building different targets add to it, so `.version` records its version, and a build of another empties it:

- macOS: `<slug>-<version>-macos-<arch>.dmg`. hdiutil images a folder holding the bundle, copied by `ditto --noclone`, a link to `/Applications`, the background picture in a hidden `.background` (`dmgbackground.go`: `macos.dmg_background`, joined with its `@2x` twin by `tiffutil`, else an arrow drawn in Go at both scales), a `.DS_Store` the tool writes (`dsstore.go`, MyGo's) placing the icons a quarter in from each side, each with its name centered from top to bottom (`dmgLabelDrop`, measured in Finder), and the hidden files stacked below the window at its left, so it scrolls no wider, which it sizes to the picture plus macOS 26's 32-point title bar, and `macos.dmg_icon` or the app's icon as `.VolumeIcon.icns`. Finder finds the picture through a Mac alias (`macalias.go`, as Python's `mac_alias` writes it for dmgbuild, checked against it byte for byte), whose node IDs and dates only the mounted image tells, so the layout is written again there over a placeholder of its size, and the volume's icon flagged; LZMA compresses it, through `diskutil image create from` where macOS 27 fails `hdiutil convert`. `sign.identity` signs it, and `notarize.go` notarizes it ([signing](#signing)).
- Windows: NSIS, as MyGo's CLI, whose makensis runs on macOS too. Every build writes `<name>.nsi` beside the executable, naming the files relative to itself, with `windows.installer_icon` and `windows.uninstaller_icon`, else the app's icon, as `<name>-setup.ico` and `<name>-uninstall.ico`, and compiles `<slug>-<version>-windows-<arch>-setup.exe` where makensis is on `PATH` or in NSIS's folder on Windows. When `windows.command_line` is true, the package also holds the console `<name>.com` companion. It installs for the user in `%LOCALAPPDATA%\Programs\<name>`, and again where the uninstall entry under `HKCU`, keyed by the bundle ID, says it is (`InstallDirRegKey`), which a silent install keeps as long as nothing passes `/D`: MyGo's `install.ps1` passed `/D` with the default folder, moving an app installed elsewhere. It quits the app running from that folder first, through PowerShell, asking unless silent, and its uninstaller deletes the files the build listed and their folders once empty, never `RMDir /r`, so a folder the user picked keeps what else it holds. It speaks the catalogs' languages the Modern UI translates, with words of its own for the desktop shortcut and the running app (`nsisWords`); `arm64` installers refuse other systems.
- Linux: a `.deb` and an Arch `.pkg.tar.gz`, archived in Go as no Mac has dpkg or makepkg, installing the directory in `/opt/<slug>`, `/usr/bin/<slug>`, a desktop entry with `StartupWMClass` and the icon in hicolor at 256 and 512 pixels. They depend on GTK 4 and suggest WebKitGTK 6, and name `linux.maintainer`, else the app's name. Beside them, an AppImage: AppImage's type 2 runtime, a static executable `fetch` downloads once by its pinned SHA-256 (`appImageRuntimes`), followed by a SquashFS 4.0 image `squashfs.go` writes, as no Mac has mksquashfs: zlib-compressed 128 KB data blocks with no fragments, 8 KB metadata blocks, inodes numbered children first, so a directory's listing knows its entries' inodes, and extended directory inodes for listings past 64 KB. Its AppDir is the Linux package with `AppRun`, a link to the executable, and `.DirIcon`.

When the build has a macOS, Windows or Linux target, the releases directory also holds `install.sh` and `install.ps1` (`install/`, NSH's install scripts made the app's), which download from `releases/download/<tag_prefix><version>/`, the version theirs unless `<SLUG>_VERSION` gives one, so the latest release's scripts install it, from `release.github`, else the GitHub repository the Git remote `origin` names, and check each file against its `.sha256`. The shell one copies a macOS app from the disk image, Apple silicon's even under Rosetta, or installs the Arch package with pacman, else the Debian one with apt-get or dpkg; the PowerShell one runs the installer with `/S` alone, and keeps to ASCII (`psQuote`), as `irm` decodes GitHub's untyped files as Latin-1. `<SLUG>_DOWNLOAD_URL` replaces the release's address, for mirrors and tests.

### Store packages

A `store` build (`-channel store`) makes each desktop and Android target's package for its store instead of its installers, and no install scripts:

- macOS (`macstore.go`): `<slug>-<version>-macos-<arch>.pkg`, the app in the App Sandbox with the network, the files the user picks, the microphone and camera `apple.info` explains and `macos.entitlements`, `sign.macos_profile` embedded as `embedded.provisionprofile` with its application and team identifiers, signed with the profile's identity, and packaged by productbuild, signed with `sign.installer`, else the keychain's installer identity of the profile's team. Without a profile it is signed ad hoc and unsigned, which runs sandboxed but uploads nowhere. It is never notarized, and refuses widgets, whose timelines a sandboxed app cannot share yet. `internal/platform/macos` loads CoreFoundation with the executable (`sandbox.go`): its initializer has libsecinit enter the sandbox, which a Go executable loading AppKit alone never does, so AppKit's Launch Services check aborts it.
- Windows (`msix.go`): `<slug>-<version>-windows-<arch>.msix`, written as makeappx would: the package's files stored, its logos under `Assets`, `AppxManifest.xml` with `windows.store`'s identity, a full-trust app, its languages and `file_types`, `AppxBlockMap.xml` hashing every file in 64 KB blocks past its local header, then `[Content_Types].xml`. It is unsigned, for the Store, which signs it; Windows installs no unsigned package with an executable, so testing registers its unpacked manifest with `Add-AppxPackage -Register` ([roadmap](../roadmap.md#installers)).
- Linux (`flatpak.go`): `<slug>-<version>-linux-<arch>.tar.gz`, the package with its AppStream metadata, and once the targets are built `flatpak/<id>.yml`, a manifest on GNOME's runtime (`linux.flatpak_runtime`, 51 by default) that installs each architecture's archive from the release, or from beside it without a GitHub repository or feed, for Flathub or flatpak-builder to build. A `.flatpak` bundle is an OSTree commit, which no Mac writes.
- Android (`apk/bundle.go`): `<slug>-<version>-android-<arch>.aab`, the base module's manifest and resource table as aapt2's protocol buffers, from the same manifest and table the APK's binary XML encodes, `BundleConfig.pb` keeping native libraries compressed, which the runtime needs extracted, and a JAR signature with `sign.keystore` (`apk/jar.go`), Play's upload key. `android.target_sdk` raises the manifest's `targetSdkVersion` to the level Play requires.

### Updates

`updates.go` builds each package for the channel `updates.channel` or `-channel` names, as [updates](updates.md#channels) describes; development builds never update. Only the direct channel adds anything to a package beyond `-X` flags giving `nsgo.Run` `updates.automatic`; every build, development ones too, gets the app's identity, version and build number in `core` (`core.App`).

- Each direct macOS, Windows, Linux and Android release writes `appcast-<target>.xml`: Sparkle's RSS format, with one item, this version's installer, signed with EdDSA by `NSGO_UPDATES_KEY`'s key, which must be `updates.key`'s secret one.
- There is one feed per target, since machines build targets apart, so nothing filters by `sparkle:os` or architecture. macOS and Windows get none without the secret key, as Sparkle and WinSparkle refuse unsigned updates.
- The feed is `updates.feed`, else `release.github`'s `releases/latest/download/`. The keys are `nsgo keygen`'s, which is Sparkle's format too: `updates.key` holds the public key itself, and the secret one lives only where releases build.
- macOS packages carry Sparkle 2.10.1, unpacked by macOS's tar to keep its links and signatures, and signed inside out as Sparkle documents. Info.plist names the feed, key and schedule.
- Windows packages carry WinSparkle 0.9.4 beside the executable. The appcast runs the installer with `/S /RELAUNCH`, which starts the new version once installed.

Sparkle and WinSparkle are downloaded once into the user cache and checked against pinned SHA-256s, not committed as `classes.dex` is: they are other projects' builds, 16 and 27 MB of archives, that only a direct app needs, and WinSparkle builds with Visual C++ alone. Targets build at once, so one at a time downloads and unpacks them.

### Widgets

`widgets.go` adds a widget extension to the macOS and iOS packages of an app whose `nsgo.yaml` lists `widgets`, as package `widget` describes ([layers](layers.md#dependency-graph)). WidgetKit declares widgets in Swift alone, and its views are SwiftUI's, so neither purego nor the Go runtime can make one, and the extension runs none of the app's code: the app writes timelines, and a generic extension draws them.

- `widgets/Widgets.swift` decodes a kind's `timeline.json` and builds SwiftUI views of its nodes, with a policy of `.never`, as the app reloads it; it reads images with ImageIO at no more than 1024 pixels across, as the system bounds a widget's memory. `Kinds.swift`, written from `nsgo.yaml`, declares a `Widget` per kind in one `WidgetBundle`, which holds ten. The extension links with `-e _NSExtensionMain`, as Xcode links app extensions.
- `WidgetCenter`'s methods take `self` in a register purego does not set, so `widgets/Reload.swift` exports `nsgo_widgets_reload` with `@_cdecl`, in `libNSGoWidgetKit.dylib` on macOS and `NSGoWidgetKit.framework` on iOS, which the package loads from the bundle's frameworks with the first `Update`.
- Both compile with `xcrun swiftc` for the target, kept in the user cache by their sources, the target and the toolchain, as actool's icons are. The extension is `PlugIns/Widgets.appex`, `<id>.widgets`.
- Where timelines live, the Info.plists of the app and the extension say. On iOS, an app group's container (`NSGoAppGroup`, `apple.app_group` else `group.<id>`), which the simulator grants from ad hoc signatures' entitlements and devices from `sign.profile` and `sign.widgets_profile`. macOS opens a group's container only to apps a profile grants it, which no ad hoc signature has, so the macOS app writes `~/Library/Application Support/<id>/Widgets` (`NSGoWidgetsPath`), which the extension, in the App Sandbox as macOS runs widgets, reads through a read-only temporary exception, from the user's home rather than its container's (`getpwuid`).
- The extension is signed before the app, which is signed without `--deep`, so its entitlements stay its own. `nsgo dev` registers it with `pluginkit -a`, as it starts the app's binary rather than the bundle. For Xcode's device signing, the generated project gives it a target of its own, `<id>.widgets`, which copies the build's extension, is signed automatically and embedded in the app, both claiming the app group, which automatic signing registers; `-embed` packages carry none.
- `live_activities` gives the iOS app the extension too, `NSSupportsLiveActivities` and the app group. ActivityKit's `Activity` is generic over Swift types, so one `NSGoActivityAttributes` (`widgets/Activity.swift`, in both the extension and the library) holds a kind and an ID, and its content-state is the JSON package `widget` writes: the fields, which `widgets/ActivityViews.swift` lays out, and the views the app gave, drawn as timelines' are. Defaults drawn in Swift keep a state within ActivityKit's and APNs' 4 KB, and let a server push one without NSGo's views. `widgets/Activities.swift` exports the library's functions to start, update, end and list them and a callback for presses and push tokens; the library is weakly linked to ActivityKit and App Intents, younger than iOS 15.
- A button's `NSGoActionIntent` is a `LiveActivityIntent`, which iOS runs in the app's process: the library's copy, built with `NSGO_APP`, waits for Go's callback, which `OnAction` sets before `nsgo.Run` as no view runs in a background launch, and then for the updates the handler started. App Intents finds intents by the metadata Xcode extracts, so the tool compiles both with `-emit-const-values-path` and the toolchain's `SwiftConstantValues/AppIntents.json`, and runs `appintentsmetadataprocessor` as Xcode does, into `Metadata.appintents` of the extension and of the app; they match by the intent's name, whatever its module.

### App Clips

`appclip.go` nests an App Clip in the iOS package of an app whose `nsgo.yaml` has `app_clip`. The clip is an iOS app of its own, built by `buildIOSApp` from `clipProject`: the app's project under the clip's name, ID (`<id>.Clip`) and main package (`app_clip.main`, whose `resources/` it takes), without widgets or a clip. It goes to `AppClips/<name>.app`, its Info.plist holding `NSAppClip` and its `MinimumOSVersion` `app_clip.minimum` (16.0, as iOS 15 downloads clips of 10 MB alone).

- A device build larger than the system downloads, 15 MB or from iOS 17 100 MB, fails; the simulator's warns.
- `sign.clip_profile` signs a device build's clip before the app, as the widgets' profile does, its associated domains `appclips:` `app_clip.domains`; the app's profile must list the clip (`associated-appclip-app-identifiers`). The simulator refuses to launch an app whose ad hoc signature claims a `com.apple.developer` entitlement, so simulator builds claim none. Xcode's device signing leaves the clip out of the app with a warning ([roadmap](../roadmap.md#app-clips)).
- `nsgo dev -clip <url>` runs the clip alone, opened from the link: in the simulator it installs the build's clip and launches it with `_XCAppClipURL`, as Xcode does, and the iOS backend takes that as the opening link when no activity brings one, as `simctl` sends none. On an iPhone Xcode signs the clip as an App Clip product (`on-demand-install-capable`), with entitlements naming its parent through `$(AppIdentifierPrefix)` and its domains, and `devicectl` launches it with `_XCAppClipURL`; a personal team, which Apple lets sign no clip, is refused first, as Xcode's preferences mark it (`freeTeam`). It then prints the link as a QR code of half blocks, which the camera opens the clip from once the device's Local Experiences list the link.
- The backend reads a link from the scene's `NSUserActivityTypeBrowsingWeb` activities, as it connects and in `scene:continueUserActivity:`, into `Environment.OpenedURL`, and `NSAppClip` in the main bundle's Info.plist into `AppClip`.

## Signing

`sign.identity` signs macOS packages, libraries first: macOS keeps the permissions it grants an identity's app across builds, where each ad hoc signature counts as a new program. `nsgo dev` and `nsgo test` stay ad hoc, as macOS credits what a terminal starts to the terminal.

`sign.profile` signs the iOS package: `security cms` opens the profile, whose `application-identifier` must cover the bundle ID; a wildcard profile signs the app's own ID, which devices require. The profile goes in as `embedded.mobileprovision`, and `codesign` signs with `sign.identity`, else the keychain's identity for one of the profile's certificates.

`sign.notarize`, a notarytool keychain profile, or an API key in `NSGO_NOTARY_KEY`, `NSGO_NOTARY_KEY_ID` and `NSGO_NOTARY_ISSUER`, notarizes the macOS package of a release build (`notarize.go`), refused without a Developer ID `sign.identity` before anything builds. Every executable is then signed with the hardened runtime and a secure timestamp (`macSignArgs`), the app with the device entitlements `apple.info`'s usage descriptions ask for; the disk image, else the app zipped by `ditto`, goes to `notarytool submit --wait`, and the ticket is stapled to the image and the app. A rejection's error carries `notarytool log`.

`sign.keystore` signs release APKs (`apk/keystore.go`): PKCS#12, with PBES2 (PBKDF2 and AES or 3DES) as keytool and OpenSSL 3 write it or PKCS#12's SHA-1 schemes with 3DES and 40-bit RC2 as older tools do, or JKS, whose key protector is a SHA-1 stream of the password. `NSGO_KEYSTORE_PASSWORD` and `NSGO_KEY_PASSWORD` give the passwords, never `nsgo.yaml`; `sign.key_alias` picks a key. APKs sign with RSA keys only.

## Signed packages

`publish.go` drives `tsx/pkg` ([signed packages](tsx.md#signed-packages)). Keys are base64 text, never files: `keygen` prints a pair, a 32-byte Ed25519 public key and the seed of its secret one, and writes nothing. Public keys are given as text, in flags, `nsgo.yaml` and apps' code; secret keys only in the environment, `NSGO_ROOT_KEY` for a root's and `NSGO_RELEASE_KEY` for a release key's, as `NSGO_UPDATES_KEY` gives updates' ([updates](#updates)), so none sits in a file beside the project, in shell history or in a process list. `certify` has the root certify the release key `-key` for `-apps` and `-days`, writing `-out`, `release.cert` by default, as JSON. `publish` compiles the app's TSX entry, the one its main package runs or `-entry`, else `App.tsx`, and signs it as the app of `nsgo.yaml`, its build `build_number` else Android's code of its version, with its `capabilities` (`capabilities.go`, read strictly and in snake case, as every command loading `nsgo.yaml` does), into `build.output`'s `<name>-<version>.nsgopkg`; given a package instead, it signs that again, to `-out`. It refuses to sign what devices would refuse. `verify` checks a package against the public keys `-root` lists and `-revocations`, or without roots against itself alone, and prints what it holds, its capabilities included; `revoke` has a root sign list `-sequence` of release key IDs and packages, by SHA-256 or file.
