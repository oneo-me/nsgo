# HarmonyOS

**Status: preview.** `nsgo build -target harmonyos` assembles a HAP in Go, the engine runs in WebAssembly in ArkWeb, and the ArkTS render layer draws what it mounts with ArkUI views: `examples/hello` shows native text, a native text field and a native button. The renderer covers a first vocabulary only, listed under [Approach](#approach). The target stays out of `all`, as its packages are unsigned previews, and the numbers on this page are from the OpenHarmony 7.0 (API 26) x86_64 emulator, except the frame-rate rows in Measurements, measured again on the HarmonyOS 6.1.1 emulator whose launcher adds cards.

NSH's HarmonyOS backend is a community platform outside NSH ([nsh-platform-harmonyos](https://github.com/huacnlee/nsh-platform-harmonyos)); NSH does not ship or test it. NSGo ports the design, not the code ([NSGo and NSH](nsh.md)), as it did with `nsh-platform-miniprogram` ([mini programs](miniprogram.md)).

## What runs now

The tool writes a HAP, never a project: DevEco is needed only to rebuild the host (`cmd/nsgo/harmony/host/build.sh`), whose bytecode, resource table and `module.json` are committed.

- `nsgo build -target harmonyos` compiles the app with the `nsgoharmony` backend, puts the module and its page under `rawfile/web`, and releases `<name>-<version>-harmonyos.hap`.
- The host's `Index.ets` lays a 1×1 `Web` under the ArkUI tree and serves the page from the rawfile directory in `onInterceptRequest`. Its `nsgoHarmony` proxy answers the module: `ready`, `submit` (a batch's operations), `tick` and `idle` (the frame clock), `device` (the window and the system), `measure` (text), `perf` (readings) and `launch` (what the Want that opened the app said).
- Every view is placed at the frame the engine gave it, in the window's coordinates, and text is drawn by a native `Text` in the font the engine measured with, so the layout and the glyphs are the platform's.
- The tool names the app in `module.json` and `pack.info` — version and label — and the bundle name too: with the OpenHarmony SDK it builds a host for the app's id and keeps the id, and without it patches the committed host and pads the id to the host's fixed length. The label may be literal once packaged, where the project's schema wants a resource.
- `examples/hello` builds a 9.4 MB HAP, and it installs and starts on the emulator with the engine reporting `ready` and a first batch of nine views. With `hdc` on PATH, `build -run` installs the HAP and starts its ability.

What this does not give: anything signed for Huawei's devices. That is the rest of this page. A native `Scroll` works, with the rows a scroll adds appearing as the engine sends them; `Image` shows a URL, the bytes it embeds, or a file in the app's resources, in the pixel density the device asks for; a `Canvas` replays the engine's drawing, gradients, text and images included; a text's spans are `Span`s; a modal covers the app as its children draw it, and the back gesture closes it; an alert is the system's own dialog, with the button's index sent back; text and an image go to the system clipboard, a link opens in whichever app takes it, a field takes and loses focus, a selection the app asks for highlights its text, a web view loads its page, a video plays and reports its progress, and the status bar shows or hides as the app asks, an image's size is known before it shows, and a view's test id, label and pointer behavior reach ArkUI's attributes, and the keyboard closes when the engine asks, while reading the clipboard is refused to an ordinary app, so a read answers empty; the system's photo picker answers with the bytes of each image the user picks, the document picker copies what the user picks into the app's cache, the save dialog writes what the app gives it where the user chose, a file opens in the app the system associates with it, a photo comes from the system's camera picker, and a 2×2 home-screen card shows what the app last gave `widget.Update`, or `nsgo.yaml`'s `widget.title` until it does, or the app's name without it.

## Approach

A HAP carries a WebAssembly build of the engine, ArkWeb hosts it, and an ArkTS render layer applies mount batches to ArkUI components. The `nsgo` tool assembles the HAP in Go, as it writes APKs and disk images in Go ([tool](tool.md)).

The renderer keeps the views as a tree and draws them nested, each at the frame the engine gave it, because the engine has already laid every view out; a scroll view draws its children in an ArkUI `Scroll` and reports the offsets the user leaves it at. It draws what it knows and leaves the rest to come: `View` (background, border, corners, opacity, hidden), `Text` (content, font, color, alignment, lines), `Input` (value, placeholder, masked) and `Modal` (a layer over the app, its children drawn as any other view), with a press reported for nodes that ask for one and the system's `AlertDialog` for an alert. A batch mounts, updates or removes the `FrameNode`s it names: a container is a `Stack`, a scroll a `Scroll` around a content `Stack`, a text or input ArkUI's own component, and rich text, canvases and an image drawn from its bytes a `BuilderNode`. `typeNode` sets each node's attributes directly, so nothing reads a batch version and ArkUI re-evaluates no statement; the engine sends deltas, and a phone-sized screen keeps the whole tree.

A text field is controlled: the engine does not echo a value it believes the field already shows (`commit.go` sends `ItemInputValue` only when `in.value != in.shown`). The host therefore keeps the tree's value in step with each `onChange` before reporting it, and the platform counts edits so a value computed from an older edit is dropped rather than overwriting what the user typed since. Without both, a batch rebuilds `TextInput` with a stale value, which fires `onChange('')` and clears the field — it looks like the typed text flashes and vanishes. ArkUI's `TextInput` also needs an explicit `lineHeight` and no vertical padding: the engine gives a fixed frame, and the default padding otherwise leaves only the top half of each glyph visible in a short field.

Hit testing keeps the nesting: each view also carries the nearest ancestor that reports presses, so a press on a button's label goes to the button.

The window is laid out full screen, as the engine lays every target out, and the host measures what the system bars and the keyboard cover and sends it as the environment: once the module is up, and again whenever the window or the bars change, through `nsgoEnv` (Go's `SetEnvironment` and `Resize`). The environment is the system's own: the locale, appearance, font scale, RTL, screen reader, OS version, device type and lifecycle come from `i18n`, `Configuration`, `accessibility`, `deviceInfo` and the ability's callbacks, and a system configuration change, a new Want or a move to the background all ask the engine to read it again.

A Want's `nsgo-` parameters are the engine's flags at launch: `hdc shell aa start -b <id> --pb nsgo-fps true` starts the monitor on a HAP that was built without it, and `nsgo build -run -fps` passes the same parameter. `want.uri` is `Environment.OpenedURL`, so `aa start -U nsgo://...` and an app's own App Linking skill reach `mobile.OpenedURL`. `nsgo build -fps` also writes `perf.json` beside the page as the fallback for a launch with no parameters at all; a later build without `-fps` removes it.

| Part | Choice |
| --- | --- |
| Engine | `GOOS=js/wasm`, the no-DOM build the mini programs use |
| Carrier | ArkWeb, attached at 1×1; the page reads the module from a URL the host answers in `onInterceptRequest` |
| Bridge | page→ArkTS `JavaScriptProxy`, which answers synchronously; ArkTS→page messages |
| Images | a URL goes to ArkUI's `Image` as it is; bytes and `asset:` paths become a `PixelMap` the host decodes, the latter read from the HAP's rawfile directory |
| Text | laid out on the engine side; runs are measured in one call, not one round trip each |
| Canvas | command replay on an ArkUI `Canvas`, as `canvas2d` plays the web's |
| Nodes | an imperative tree of `FrameNode`s: `typeNode` for a `Stack`, `Text`, `TextInput`, `Scroll` or `Image`, `BuilderNode` for a span text, a canvas, an image from bytes or the app's resources, or a screen's system header, mounted through `NodeController` and `NodeContainer` |
| Package | HAP assembled with `archive/zip`; its configs are plain JSON |

The render layer must send deltas and keep only the nodes near the screen: the spikes measured a full repaint of 1000 nodes at 50 fps, so a full tree per frame is not an option. What animates is declared once and run by ArkUI, as `architecture.md#boundaries` asks of every backend.

## Constraints

- `Native` names a view of a component the app registered; a Go app has none to give the host, which is prebuilt ArkTS, so a native view would have to come from ArkTS the app ships and mounts through a `NodeContainer`, which the target has not.
- `Shader` fills a view with WGSL on the GPU. ArkTS has no WebGL or WGSL, and `drawing` offers gradients and image filters only, so a shader view could draw that subset at most.
- A test mounts an app on the device (`testhost.go`, under the `nsgotest` tag): `nsgo test -target harmonyos` builds the tests as the HAP's module, and the host opens the app in the page. A press goes to the view the engine's frames put under the point — the deepest view that asks for a press, the latest inserted among stacked ones, each parent's frame added and each scroll view's offset taken off — as ArkUI's hit test names the view a page's press went to; a field takes the focus the page reports, and typing appends to it as an edit. Drags and keys go in as touches and keys, and a scroll drives the page's own `Scroller` (`scrollBy` on the bridge), since ArkUI scrolls its own view and a synthesized touch does not move it; the page then reports the offset to the app. A screenshot is the root `FrameNode` through `componentSnapshot`, packed to a PNG and answered through the bridge. Checked on the emulator: `examples/hello`'s `TestGreets` types a name, presses twice and reads what the app says; a 20-row list scrolled by a test reports the offset to its app; `examples/orbit`'s `TestKeysTurnTheRing` turns the ring with keys; and a modal whose `OnRequestClose` closes it answers the back a test sends.
- A commit that re-lays out a list used to cost 11 ms and hold the frame clock to 35 FPS; two things took it to 4.8 ms and 62 FPS. The text engine caches what the host measured by text, font and wrap width, since each measurement is a bridge round trip and a relaid row measures the same text. The renderer also writes a view's attributes only when the batch names it: `Tree` marks a view dirty, and a frame skips the tree's other nodes, where before every batch set every attribute on every `FrameNode` again.
- A zoomable scroll view scales its content: the renderer grows the content `Stack` to the content's size times the scale and scales it about its top left, so ArkUI scrolls the zoomed range, and keeps the point an engine zoom asked for at the same place. Two fingers zoom it when the app allows pinches, and the page reports the scale and offset as an `EventScroll`, so the engine clamps it and the app hears it. An engine's `Ref.ZoomTo` is checked on the device; a pinch is wired to two fingers but `uitest` injects none, so it is not measured.
- A canvas is replayed call by call, and ArkUI charges for each call and for compositing its surface, so the obvious ways to make one cheaper do not work here. Two 340 pt canvases, a still background under a moving one, cost 8.42 ms of main-thread work a frame against 9.27 ms for one canvas redrawing everything in the same session, since both surfaces are composited every frame. Merging 120 tick strokes into one path with one stroke cost 12.05 ms against 9.27 ms, as ArkUI tessellates a 120-subpath path more expensively than 120 short segments. A canvas therefore keeps one operation a shape; what makes one cheaper is fewer elements, or an `Image` for a still background, not a different order of calls.
- A canvas's image is a `PixelMap` the renderer decodes, from the bytes the drawing embeds or from an `asset:` path in the HAP, and draws at the op's rectangle; its natural size is the pixels over the screen's density, since the op is in points. A drawing that names a URL logs once and draws nothing: ArkUI's canvas takes a `PixelMap`, not a URL, and fetching one would need the app's own network call.
- `typeNode` creates only the components its table names: `Stack`, `Text`, `TextInput`, `Scroll`, `Image` and the like. `Web`, `Video`, `Native` and `Shader` are not among them, so a view of those kinds has to be a `BuilderNode` around a declarative component, as rich text, canvases and images from bytes already are.
- A card runs in an ArkTS environment of its own with no `Web` view, so the engine cannot draw it: `EntryFormAbility` gives the card a `formBindingData` and `WidgetCard.ets` draws it with ArkUI. The card provider and the app are different processes, so `widget.Update` reaches the host's bridge, which writes the data and the card ids to files in the app's own directory; `onAddForm` records the form id and `onUpdateForm` answers the system's timed refresh with `formProvider.updateForm`. `nsgo build` still writes the first title to `widget.json` in the HAP's rawfile directory, which the provider reads until the app writes its own data. The form extension is `visible`, `enabled`, and registered under `ohos.extension.form` in its own `:form` process, as `bm dump` shows. The HarmonyOS emulator's launcher (`com.ohos.sceneboard`) adds one: a long press on the app's icon offers 卡片, which shows the card as the app's title and 添加至桌面 puts it on the home screen; `onAddForm` then receives the form id and records it, checked with a 2×2 card (form `1692780870`).
- A save carries its bytes: `SaveOptions.Path` would have the engine read a file in the app's storage, which `js/wasm` cannot, so only `SaveOptions.Data` saves here.
- A system picker is a `UIExtensionAbility`, and backing out of it can deliver the same back to the page's `onBackPress`, which would leave the app through `ItemBackUnhandled`. The page therefore ignores back while a picker shows (`picking`), so cancelling one returns to the app.
- The clipboard takes text but gives none back: `getData()` and `hasDataSync()` are refused with `ohos.permission.READ_PASTEBOARD`, a system_basic permission an ordinary HAP cannot hold, so `ItemReadClipboard` answers an empty text or false. Writing goes through `setData`, which the pasteboard service accepts from the app.
- ArkUI's `Scroll` reports no offset for a pull past its top, the content springing where the finger goes, so the page judges a pull from the finger's own travel past the view's top. It shows no spinner of its own yet: a refreshing view's room above the content is the engine's, and an app's own indicator stays where it is laid out.
- A scroll view's phase is ArkUI's `ScrollState`: `Scroll` is a drag, `Fling` the glide after it and `Idle` its rest, and the page sends the transitions between them, so a drag a glide catches ends its momentum first. A scroll the engine sets moves in `Idle` and reports no drag, which is what the engine's handlers expect.
- Touches reach the page's `onTouch` in window points, which are the engine's own: the page fills the window and the status bar draws over its top. The engine finds the view under each finger from its own frames and runs the responders there, so a drag on a `Slider`, a sheet or a carousel follows the finger without the render layer knowing which. `onClick` still reports a press, separately from the touches.
- A screen's header is the render layer's: the core pads the content below `Environment.HeaderHeight` and sends `ItemScreen`, and the page draws a bar with the title and a back button that sends the same `EventBack` the gesture does, with the screen's id. A `BuilderNode`'s frame node takes the size its component lays itself out at, so a `width` or `height` set on it does not shrink it: the header's own `Stack` names its height, or it would fill the window and swallow every press.
- The back gesture goes to the page's `onBackPress`, which sends `EventBack`: the engine closes the topmost modal, pops a screen, or answers with `ItemBackUnhandled`, which ends the ability. A modal is an ordinary view whose children cover the app, so a backdrop press and Escape go through the engine like any other press. A sheet's swipe and size reports are iOS's, so a HarmonyOS alert always shows as the system's dialog, as an action sheet would not.
- An `asset:` image has no path ArkUI can read: the page has no filesystem and `Image` cannot name a file inside the HAP. The build lays the app's resources beside the page, so they are `resources/rawfile/web/resources/<path>` in the HAP, and the host reads the one the engine picked — its density variant included — with `resourceManager.getRawFileContentSync`, decodes it into a `PixelMap` and draws that. A URL still goes to ArkUI's own loader, which caches and decodes off the UI thread.
- `fetch('resource://rawfile/...')` is refused (`URL scheme "resource" is not supported`), while `<script src>` loads. The host must answer the page's requests in `onInterceptRequest`, which sees `resource://rawfile/...` too, so the handler serves by path. `WebResourceResponse.setResponseData` takes a `Resource`, so the bytes never pass through a string.
- A `Web` hidden with `Visibility.None` never loads its page. The carrier must be attached and laid out; 1×1 satisfies it, and a covered carrier kept answering for a minute of touches.
- `measureTextSize` returns px and takes `constraintWidth` in vp; given one, it answers with that width rather than the text's own, so intrinsic widths come from a call without it. It matches a laid-out `Text` exactly, wrapped lines included, but is deprecated since API 18: use `UIContext.getMeasureUtils()`. `i18n.System.getSystemLocale()` is deprecated for the same reason; `getSystemLocaleInstance()` needs an `Intl.Locale` in ArkTS. `ReduceMotion` stays false: the SDK's declarations name no system setting for it. The `nsgo` URI scheme in `module.json5` is for links the app opens itself; App Linking over `https` needs the app's own domain and a profile, which a template cannot name.
- The environment arrives after the module starts: the module reads the device once at start, before the page has measured the bars, so the host sends `nsgoEnv` as soon as the module reports ready and on every change after. `AvoidAreaType.TYPE_SYSTEM` gives the status bar but not the navigation indicator in a full-screen window, which reads 0 at the bottom here.
- The host's compiled bytecode names each module `<bundle>/<module>/<path>`, so a build uses one of two hosts. With `hvigorw` on PATH and `OHOS_BASE_SDK_HOME` set, `harmony.CompileHost` builds a host for the app's own id from `host/templates` and caches it under the user's cache directory, keyed by the id, the templates and the SDK version; `harmony.PackageWithHost` assembles from it and the installed bundle is the id itself. Without the SDK, the committed host serves: it is compiled with a fixed 64-byte placeholder bundle, and `harmony.Package` replaces it byte for byte with an equally long name — the id, a fixed marker and zero padding, so `com.example.alpha` becomes `com.example.alpha.nsgohost000...` — because equal lengths keep the bytecode's string lengths and offsets valid. `build.harmonyos_bundles`, or `-harmonyos-bundles`, chooses auto (the default), exact (fails without the SDK) or padded; auto keeps the app building when a host fails to compile and says why. A name too long for the placeholder is refused. `doctor` says which name a machine gets. ArkTS's normalized OHMUrl would remove the prefix, but a host built with `useNormalizedOHMUrl` does not start on the OpenHarmony emulator here.
- HAP entries are stored uncompressed and `module.json` and `pack.info` are plain JSON, so the tool can patch the app's name, version and label and repack without hvigor. The packaged `module.json` takes a literal `label`, though the project's schema wants a resource, so the tool names each app there and leaves the resource table alone. `rpcid.sc`, the system capability list, is the one part whose generation is not understood yet.
- A batch costs about 0.03–0.05 ms per node on the emulator, parse and tree updates only: 404 nodes (34 KB of operations) applied in 18 ms, 2004 nodes (177 KB) in 57–108 ms. A plain scroll of 1000 views mounts whole and its scroll is ArkUI's own, with no batch per frame, while a 1000-row `base.List` mounts only the rows near the screen: 14 rows in 47 nodes at rest, 8 in 30 after a scroll, as `core.List` windows its cells.

- Animations travel as a graph in `ItemAnimation` and run on `driver.Animator`, stepped once a display frame from ArkTS's `displaySync`: the animator moves its values, the mounter writes each changed view's style with them — opacity, translate, scale and rotate — and each changed canvas's drawing with its slots, and the clock stops when nothing runs. A timing run from 0 to 200 over 2 s reached 200 in 176 frames of 16–20 ms each.
- `nsgo build -fps` writes `perf.json` beside the page, which starts the module with `--nsgo-fps`: the engine then installs its `PerfMonitor`, records each frame's work and closed frame, and hands the readings to the host every 500 ms (`perf` on the bridge), which draws them in a panel at the top right. The clock keeps running while a monitor is installed, whether or not something animates, as on the other targets; the process' CPU, GPU and memory stay unknown, since `js/wasm` cannot read them.

- The SDK carries `hap-sign-tool.jar`, `OpenHarmony.p12` and the profile certificate chains. Signing a profile works; signing an app needs an app certificate chain, which the SDK does not carry but `generate-app-cert` builds from a generated CA. Huawei devices take only AppGallery Connect certificates. Emulators install unsigned HAPs.

## Open questions

- The execution model: this WebAssembly carrier, or a native Go `.so` loaded through N-API that reaches ArkUI's C API with purego, as NSH's Rust backend does. The native route cannot satisfy the rule that a target builds with Go and Xcode alone, because Go has no upstream `ohos` target and a fork would be needed.
- Whether the preview stays as a tier of its own once the native layer exists. It is the only thing that runs today and costs nothing to keep, but it shows DOM where the native layer shows ArkUI.
- Native `Scroll` around engine-positioned nodes: offsets cost 1–4 ms, a window of 30 rows holds 60 fps, and the platform's spring overscroll shows in the offsets themselves, so the engine clamps its window index rather than the offset. A rebuilt window costs one dropped frame where reusing rows would not.

- `ItemOverflow` needs no answer: UIKit, AppKit and Android only look for a touch's target inside a view's bounds, so the core tells them the area a view's children cover outside it. ArkUI hit-tests the whole node tree instead, and a child of a parent with no size still answers a press at its own frame, so the item is read and nothing is applied. No `ItemOverflow has no renderer yet` warning should come from a menu hanging below a field.
- What Android answers and this target still leaves, and why: `ItemShare` has no `ShareKit` in the SDK and `ohos.want.action.sendData` was deprecated in API 9, so the app hears `NoShareSheet` rather than waiting. `ItemInstallPackage`, `ItemInstallSettings` and `ItemCanInstallPackages` need the system-only `INSTALL_BUNDLE` permission. `ItemShader`, `ItemShaderInput` and `ItemShaderTransition` have no WebGL or WGSL, and `ItemNative` and `ItemNativeCommand` have no `typeNode` component for a view an app registers. `ItemCheckForUpdates` answers with an error: the OpenHarmony SDK has no updater, where Android's is Play Core's.
- `ItemDirection` is read and nothing is applied: the core already mirrors the frames of a right-to-left app, the imperative tree has no global direction to set, and alert labels arrive localized. It arrives on every first commit, so it must not warn of a missing renderer.
- A picked folder has no path the WebAssembly engine can walk, so `ItemPickDirectories` answers with name/URI pairs and the Go side builds an `fs.FS` over the host's synchronous `listdir` and `readfile` bridge, as Android builds one over its document tree. The folder picker runs in `DocumentSelectMode.FOLDER`; the host lists a directory with `listFileSync` and reads a file's bytes as base64, both through the same `JavaScriptProxy` that answers `measure` and `device`. The engine reads a directory off its own goroutine, so the calls wait on the host without a round trip per entry.
- A physical key reaches the engine from the declarative root's `onKeyEvent`, which sends the raw key code, its action and its modifiers. The Go side maps the code to the core's name — OHOS KeyCodes, or the Linux input codes the emulator's `uinput` passes through — builds the press's names with and without `mod` for Control, and matches them with `driver.FindKey` against the keymap `ItemKeymap` sent it. A release clears the held key so a repeat is told from a fresh press, and the focused view decides whether a text field is editing. Matched presses are not consumed, so an input still types; `FindKey`'s `InText` keeps an editing field's shortcut from firing.
- A sticky cell moves with `position`, not `translate`: ArkUI's `Scroll` clips a translated child at its laid-out frame, while a moved position takes part in the clip. It also lifts above the rows drawn after it with `zIndex`, and its pinned place is the viewport's top, which is the status bar's height down the window because the tree is drawn below it. A cell whose `Node` follows an animated inset keeps the inset its `Start` already counts, as the render layer has no animator value to read.
- A shared element is one `FrameNode` moved: a batch whose layout animation has an `Update` and that creates a view with a deleted view's `MatchID` sends `ItemMatch`, and the renderer creates the new view where the old one was drawn, then moves it to its own frame with `animateTo` over the batch's duration. Both rectangles are the page's, since the deleted view keeps the absolute frame its last measure gave it, so a tile in a row grows into a panel under another parent. ArkUI's imperative animation takes a duration and one of its curves rather than the driver's, so a spring runs as `Friction` and a bezier as `EaseInOut`.
- The performance monitor counts a frame as shown when the surface changed, and an animation moves the surface without a commit: the frame that writes an animated style or a canvas drawing is marked dirty before `EndFrame`, and so is a frame a scroll callback moved, so a canvas repainting every frame and a native scroll both read 60 FPS rather than 0.
- The engine reuses a deleted view's id, so the renderer drops what it holds for the ids a batch deletes — `FrameNode`, `BuilderNode` leaf, controllers and last values — before the batch draws; a stale node would answer `The FrameNode is not modifiable` to the next view given that id.
- ArkUI tracks state per statement, not per component: a `ForEach` over a plain array keeps the first batch's items, and a reused child keeps the text, frame and style it first read. The renderer worked around that with a batch version every statement read; the imperative tree replaced it, since a `FrameNode`'s attributes are set in place and no statement re-evaluates. `typeNode` has no `Span` and no `Canvas`, so rich text, canvases and an image drawn from its bytes stay inside a `BuilderNode`, updated with its `update`. A scroll's offsets and a field's keyboard input are the parts a hand still checks on a device; the V2 rewrite is no longer needed.
- Rich text: spans are measured piece by piece, as `miniprogram`'s `text.go` already does. Piecewise sums match the rendered width at one size but drift by under a point when sizes mix, since kerning across a span boundary is not measured; how much drift text may carry is a quality decision.
- The target's name (`harmonyos`) and whether it joins `all`; [mini programs](miniprogram.md) and `android_x64` are the precedents for leaving one out.
- `Environment.OS`: Android's idiom under the platform name, as `miniprogram`'s runtime already maps `ohos` to `android`, or a constant of its own.
- Shaders and WebGL, ArkWeb's memory footprint on a phone, and the ArkTS render layer as a second implementation of what other backends do in Go.

## Not measured

- Behaviour on a device, including signed installs.
- A canvas heavier than a waveform.
- Typing through a physical keyboard: `uitest inputText` does not reach a field on this emulator, so composition and a held key's repeats are untested; shortcut presses themselves are checked, as are the field's own `ItemInputValue`, `ItemFocus`, `ItemBlur` and `ItemSelection`.
- The camera picker: the emulator has no camera, so only its failure path ran.
- A video's playback: the emulator's network did not load the test URL, so the view, its controls and its commands were checked, not a playing frame.
- The system's timed `onUpdateForm`: the card is added on the HarmonyOS emulator as above, but the system's own periodic refresh did not run in the check.
- The task switcher's card and its label: the emulator's bottom gesture goes home, and `uinput` cannot hold it as the task switcher needs.
- A file or folder the user picks: the picker's window is private to screenshots, so a pick could only be cancelled, not made. The folder picker opened and its cancel answer was seen; a picked folder's own `fs.FS` was checked in a Go test against the host's read bridge, which was itself read against a real directory on the device.
